# PersonaCR — Research Foundation

This document maps each research paper to the specific PersonaCR component it influenced.
PersonaCR fills a gap no existing paper addresses: combining personalized code style learning
with multi-agent automated code review.

---

## Paper 1: CodeAgent (Tang et al., EMNLP 2024)

**Paper:** "CodeAgent: Autonomous Communicative Agents for Code Review"  
**Link:** [https://arxiv.org/abs/2402.02172](https://arxiv.org/abs/2402.02172)  
**Venue:** EMNLP 2024, pages 11279–11313  
**Code:** [https://github.com/Daniel4SE/codeagent](https://github.com/Daniel4SE/codeagent)

**What it does:** Introduces a multi-agent LLM system for code review with role-based agents
(CEO, CTO, Reviewer, Coder) and a supervisory QA-Checker agent that ensures all agents'
contributions address the initial review question.

**What we adopted:**

- The QA-Checker concept → our `qa_checker.py`. Their ablation study proved that removing the
QA-Checker "substantially reduces effectiveness in identifying vulnerable issues." We kept
this as a non-negotiable component but made it a single focused LLM call for latency.
- Multi-agent architecture with specialized roles → our 6-agent system where each agent has
a distinct responsibility rather than a single monolithic reviewer.

**What we changed:**

- CodeAgent uses role-playing dialogue between agents. We use an orchestrator pattern with
no agent-to-agent communication — the orchestrator mediates all data flow.
- CodeAgent reviews against generic standards. PersonaCR reviews against the developer's
personal coding fingerprint — this is our core differentiator.

## Paper 2: CRScore (Naik et al., NAACL 2025)

**Paper:** "CRScore: Grounding Automated Evaluation of Code Review Comments in Code Claims and Smells"  
**Link:** [https://arxiv.org/abs/2409.19801](https://arxiv.org/abs/2409.19801)  
**Venue:** NAACL 2025, pages 9049–9076

**What it does:** Develops a reference-free metric for evaluating code review quality using
pseudo-references generated by LLMs and Code Analysis Tools, then measures alignment via
semantic textual similarity (STS). Achieves 0.54 Spearman correlation with human judgment
and 0.95 Spearman for system ranking.

**What we adopted:**

- The entire Layer 3 evaluation pipeline is CRScore-inspired:
  - `pseudo_ref_gen.py` — generates pseudo-references combining LLM claims + AST analysis
  - `sts_scorer.py` — computes pairwise STS between review sentences and pseudo-references
  - Three quality dimensions: comprehensiveness, conciseness, relevance (harmonic mean)
- The insight that you can evaluate review quality without human-written references by
generating pseudo-references from the code itself.

**What we changed:**

- CRScore uses Magicoder-S-DS-6.7B (6.7B param model running locally) for pseudo-reference
generation. We use Groq's Llama 3.3 70B via API (300+ tok/sec) + local AST analysis for
a hybrid approach that is faster on consumer hardware.
- CRScore only scores reviews. We added a Quality Gate that makes a pass/fail decision and
triggers Agentic Loop 2 for re-review — turning evaluation into an agentic capability.
- CRScore uses a custom fine-tuned STS model. We use all-MiniLM-L6-v2 (80MB, same model
family) with singleton loading for 69ms inference after warmup.

## Paper 3: MPCODER (Dai et al., ACL 2024)

**Paper:** "MPCODER: Multi-User Personalized Code Generator with Explicit and Implicit Style Representation Learning"  
**Link:** [https://arxiv.org/abs/2406.17255](https://arxiv.org/abs/2406.17255)  
**Venue:** ACL 2024

**What it does:** Learns per-developer coding style using explicit features (25 Checkstyle
attributes) and implicit features (contrastive learning on code representations). Generates
code in a specific developer's style.

**What we adopted:**

- The concept of per-developer coding style as a learnable representation. MPCODER validates
academically that developers have distinct, quantifiable coding patterns.
- The explicit feature extraction approach → our `pattern_extractor.py` extracts 30 features
(expanded from their 25 Checkstyle attributes to include Python-specific metrics).

**What we changed:**

- MPCODER does personalized code generation. PersonaCR does personalized code review.
This is the core research gap we fill — no paper combines personalized style learning
with multi-agent review.
- MPCODER uses contrastive learning for implicit style. We use code-specific embeddings
(Jina v2 base code) stored in ChromaDB for similarity-based retrieval instead.

## Paper 4: RevAgent (Li et al., November 2025)

**Paper:** "Issue-Oriented Agent-Based Framework for Automated Review Comment Generation"  
**Link:** [https://arxiv.org/abs/2511.00517](https://arxiv.org/abs/2511.00517)

**What it does:** Decomposes code review into parallel category-specific agents (Refactoring,
Bugfix, Testing, Logging, Documentation) followed by a critic agent that selects the most
salient issue-comment pair. Achieves 12.90% improvement over baselines on BLEU.

**What we adopted:**

- Parallel category-specific agents → our Style Analyst + Defect Hunter run in parallel
via `asyncio.gather()`, each specialized for a different review category.
- Critic agent pattern → our QA Checker serves as the critic that validates and filters
outputs from the parallel agents.

**What we changed:**

- RevAgent fine-tunes each agent on category-specific data. We use prompt engineering
with Groq's Llama 3.3 70B instead (no fine-tuning needed, zero training cost).
- RevAgent's categories are generic (Refactoring, Bugfix, etc.). Our Style Analyst
specifically compares against the developer's personal patterns — personalized, not generic.

## Paper 5: Latency-Aware Multi-Agent Architecture Search (January 2026)

**Paper:** "Learning Latency-Aware Orchestration for Parallel Multi-Agent Systems"  
**Link:** [https://arxiv.org/abs/2601.10560](https://arxiv.org/abs/2601.10560)

**What it does:** Proposes a framework that treats inference latency as a first-class
optimization objective. Shows that optimizing for total token usage does not guarantee
latency reduction — latency is determined by the critical execution path, not total computation.

**What we adopted:**

- Critical path optimization → our Planner uses a hybrid rules-based fast path + LLM fallback.
Rules-based planning is instant (0ms) and handles obvious cases without an LLM call,
removing the Planner from the critical path for simple reviews.
- Confidence Evaluator is rules-based (0ms) instead of LLM-based, keeping validators
off the critical execution path.
- Quality Gate is rules-based (0ms) for the same reason.
- Capped agentic loops at max 2 iterations — the paper shows diminishing returns after 2.
- Parallel execution of independent agents (Style + Defect, then QA + Confidence)
to minimize the longest sequential chain.

**Impact on our system:**


| Agent                       | Without optimization | With optimization           | Saved   |
| --------------------------- | -------------------- | --------------------------- | ------- |
| Planner                     | ~1500ms (LLM)        | 0ms (rules-based fast path) | ~1500ms |
| Confidence Evaluator        | ~1500ms (LLM)        | 0ms (rules-based)           | ~1500ms |
| Quality Gate                | ~1500ms (LLM)        | 0ms (rules-based)           | ~1500ms |
| Total critical path savings |                      |                             | ~4500ms |

## Paper 6: Multi-Agent Design (Google Research, February 2025)

**Paper:** "Multi-Agent Design: Optimizing Agents with Better Prompts and Topologies"  
**Link:** [https://arxiv.org/abs/2502.02533](https://arxiv.org/abs/2502.02533)

**What it does:** Studies how agent topology (how agents communicate) and prompt quality
affect multi-agent system performance. Shows that a weaker model with strong orchestration
often outperforms a stronger model with poor orchestration.

**What we adopted:**

- Hybrid orchestrator topology → our orchestrator uses centralized control (Planner decides,
orchestrator routes) with no agent-to-agent communication. Agents do not talk to each other —
the orchestrator mediates all data flow.
- "Architecture compounds, model choice is one variable" → we invested heavily in prompt
engineering for each agent rather than using a more expensive LLM.

## Paper 7: AI Agent Fingerprinting (Ghaleb et al., MSR 2026)

**Paper:** "Can We Fingerprint LLM-based AI Agents and Copilots in Code?"  
**Link:** [https://arxiv.org/abs/2601.17406](https://arxiv.org/abs/2601.17406)  
**Replication:** [https://github.com/Taher-Ghaleb/AIAgentsFingerprinting-MSR2026](https://github.com/Taher-Ghaleb/AIAgentsFingerprinting-MSR2026)

**What it does:** Proposes 53 code features for fingerprinting AI-generated code, achieving
97.2% F1-score in identifying which AI agent wrote a piece of code.

**What we adopted:**

- Feature engineering methodology → our `pattern_extractor.py` implements 30 of their features:
comment density, comment style ratio, conditional density, loop density, comprehension ratio,
Gini coefficient for change concentration, indentation consistency, line length statistics,
import density. These are layered on top of our original 12 features.
- The insight that code has a quantifiable "fingerprint" — originally used for AI detection,
we repurpose it for developer style profiling.

**What we changed:**

- Ghaleb uses fingerprinting to detect AI agents. We use it to learn human developer patterns.
- We skipped their PR/commit/temporal features (relevant to AI detection, not developer style).

## Paper 8: Multi-Granularity Code Fingerprinting (Ringer et al., 2025)

**Paper:** "Code Authorship Attribution with Multi-Granularity Fingerprinting"  
**Link:** [https://doi.org/10.1016/j.csi.2025.103973](https://doi.org/10.1016/j.csi.2025.103973)  
**Venue:** Computer Standards & Interfaces, March 2025

**What it does:** Fingerprints code at multiple granularity levels — file-level and
function-level — and stores representations in ChromaDB for authorship attribution.

**What we adopted:**

- Multi-granularity storage in ChromaDB → our `embedder.py` stores embeddings at both
file-level and function-level with a `granularity` metadata field.
- Two-stage retrieval → `query_similar_staged()` first retrieves relevant files, then
retrieves specific functions within those files. This gives the Style Analyst both
broad context (file architecture) and precise matches (similar functions).

## Paper 9: Ericsson LLM + Static Analysis (July 2025)

**Paper:** "Automated Code Review with LLMs: An Experience Report from Ericsson"  
**Link:** [https://arxiv.org/abs/2507.19115](https://arxiv.org/abs/2507.19115)  
**Venue:** IEEE (industry report)

**What it does:** Documents Ericsson's experience deploying LLM-based code review in
production. They found that combining LLMs with static analysis tools produces better
reviews than either alone. They proposed but had not yet built a "multi-agent framework
with personalization."

**What we adopted:**

- LLM + static analysis combination → our Defect Hunter combines Python AST analysis
(local, instant) with Groq LLM analysis (semantic, deeper). Our pseudo-reference
generator similarly combines AST analysis with LLM claims.
- Industry validation that the problem we are solving (personalized multi-agent review)
is exactly what industry wants but has not built yet.

## Research Gap — PersonaCR's Unique Contribution

After reviewing all major venues (EMNLP, NAACL, ACL, ICSE, ASE, MSR):

- **Personalized code generation exists** (MPCODER, Style2Code) but not personalized review
- **Multi-agent code review exists** (CodeAgent, RevAgent) but without personalization
- **No paper combines both** — this is PersonaCR's contribution

PersonaCR bridges this gap by:

1. Learning per-developer coding patterns (MPCODER concept applied to the review domain)
2. Reviewing with specialized parallel agents (CodeAgent + RevAgent architecture)
3. Self-evaluating review quality with ML (CRScore methodology)
4. Optimizing for latency on the critical path (Latency-Aware MAS principles)
5. Exposing everything via MCP for editor integration (production readiness)
