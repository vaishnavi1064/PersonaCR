# PersonaCR — Research Foundation

This document maps each research paper to the specific PersonaCR component it influenced. In the *published research literature*, PersonaCR fills a gap no existing paper addresses: combining personalized code-style learning with multi-agent automated code review. (See the honesty note in the final section on how this differs from the commercial tooling landscape.)

---

## Paper 1: CodeAgent (Tang et al., EMNLP 2024)

- **Paper:** "CodeAgent: Autonomous Communicative Agents for Code Review"
- **Link:** https://arxiv.org/abs/2402.02172
- **Venue:** EMNLP 2024, pages 11279–11313
- **Code:** https://github.com/Daniel4SE/codeagent

**What it does:** Introduces a multi-agent LLM system for code review with role-based agents (CEO, CTO, Reviewer, Coder) and a supervisory QA-Checker agent that ensures all agents' contributions address the initial review question.

**What we adopted:**
- The QA-Checker concept → our `qa_checker.py`. Their ablation study showed that removing the QA-Checker substantially reduces effectiveness in identifying problematic issues. We kept this as a non-negotiable component but made it a single focused LLM call for latency.
- Multi-agent architecture with specialized roles → our 6-agent system where each agent has a distinct responsibility rather than a single monolithic reviewer.

**What we changed:**
- CodeAgent uses role-playing dialogue between agents. We use an orchestrator pattern with no agent-to-agent communication — the orchestrator mediates all data flow.
- CodeAgent reviews against generic standards. PersonaCR reviews against the developer's personal coding fingerprint — this is our core differentiator.

## Paper 2: CRScore (Naik et al., NAACL 2025)

- **Paper:** "CRScore: Grounding Automated Evaluation of Code Review Comments in Code Claims and Smells"
- **Link:** https://arxiv.org/abs/2409.19801
- **Venue:** NAACL 2025, pages 9049–9076

**What it does:** Develops a reference-free metric for evaluating code review quality using pseudo-references generated by LLMs and code analysis tools, then measures alignment via semantic textual similarity (STS). Reports the highest alignment with human judgment among open-source metrics (0.54 Spearman correlation).

**What we adopted:**
- The entire Layer 3 evaluation pipeline is CRScore-inspired:
  - `pseudo_ref_gen.py` — generates pseudo-references combining LLM claims + AST analysis
  - `sts_scorer.py` — computes pairwise STS between review sentences and pseudo-references
  - Three quality dimensions: comprehensiveness, conciseness, relevance (harmonic mean)
- The insight that you can evaluate review quality without human-written references by generating pseudo-references from the code itself.

**What we changed:**
- CRScore uses Magicoder-S-DS-6.7B (6.7B-param model running locally) for pseudo-reference generation. We use Groq's Llama 3.3 70B via API + local AST analysis for a hybrid approach that is faster on consumer hardware.
- CRScore only scores reviews. We added a Quality Gate that makes a pass/fail decision and triggers Agentic Loop 2 for re-review — turning evaluation into an agentic capability.
- CRScore uses a custom STS model. We use all-MiniLM-L6-v2 (80MB, same model family) with singleton loading for fast inference after warmup.

## Paper 3: MPCoder (Dai et al., ACL 2024)

- **Paper:** "MPCoder: Multi-user Personalized Code Generator with Explicit and Implicit Style Representation Learning"
- **Link:** https://arxiv.org/abs/2406.17255
- **Venue:** ACL 2024, pages 3765–3780

**What it does:** Learns per-developer coding style using explicit features (Checkstyle-style attributes) and implicit features (contrastive learning on code representations), then generates code in a specific developer's style.

**What we adopted:**
- The concept of per-developer coding style as a learnable representation. MPCoder validates academically that developers have distinct, quantifiable coding patterns.
- The explicit feature-extraction approach → our `pattern_extractor.py` extracts 30 features, expanded to include Python-specific metrics.

**What we changed:**
- MPCoder does personalized code *generation*. PersonaCR does personalized code *review*. This is the core research gap we fill — no paper combines personalized style learning with multi-agent review.
- MPCoder uses contrastive learning for implicit style. We use code-specific embeddings (Jina v2 base code) stored in ChromaDB for similarity-based retrieval instead.

## Paper 4: RevAgent (Li et al., 2025)

- **Paper:** "Issue-Oriented Agent-Based Framework for Automated Review Comment Generation"
- **Link:** https://arxiv.org/abs/2511.00517
- **Note:** Authors: Shuochuan Li, Dong Wang, Patanamon Thongtanunam, Zan Wang, Jiuqiao Yu, Junjie Chen (submitted Nov 2025).

**What it does:** Decomposes code review into five parallel category-specific commentator agents, followed by a critic agent that selects the most salient issue-comment pair, with a fine-tuning stage. Reports a 12.90% improvement over baselines on BLEU (plus gains on ROUGE-L, METEOR, SBERT).

**What we adopted:**
- Parallel category-specific agents → our Style Analyst + Defect Hunter run in parallel via `asyncio.gather()`, each specialized for a different review category.
- Critic agent pattern → our QA Checker serves as the critic that validates and filters outputs from the parallel agents.

**What we changed:**
- RevAgent fine-tunes each agent on category-specific data. We use prompt engineering with Groq's Llama 3.3 70B instead (no fine-tuning, zero training cost).
- RevAgent's categories are generic. Our Style Analyst specifically compares against the developer's personal patterns — personalized, not generic.

## Paper 5: Latency-Aware Multi-Agent Orchestration (Shi et al., Jan 2026)

- **Paper:** "Learning Latency-Aware Orchestration for Parallel Multi-Agent Systems" (LAMaS)
- **Link:** https://arxiv.org/abs/2601.10560
- **Authors / venue:** Xi Shi, Mengxin Zheng, Qian Lou (University of Central Florida), Jan 2026.

**What it does:** Proposes a framework that treats inference latency as a first-class optimization objective. Shows that optimizing for total token usage does not guarantee latency reduction — latency is determined by the critical execution path, not total computation. Reports 38–46% critical-path reduction versus the baseline.

**What we adopted:**
- Critical-path optimization → our Planner uses a hybrid rules-based fast path + LLM fallback. Rules-based planning is instant and handles obvious cases without an LLM call, removing the Planner from the critical path for simple reviews.
- Confidence Evaluator is rules-based instead of LLM-based, keeping validators off the critical path.
- Quality Gate is rules-based for the same reason.
- Capped agentic loops at max 2 iterations — diminishing returns after 2.
- Parallel execution of independent agents (Style + Defect, then QA + Confidence) to minimize the longest sequential chain.

**Illustrative impact on our critical path** (swapping three LLM steps for rules-based steps removes roughly three sequential LLM calls from the longest path). *Note: these are design-level estimates; report measured numbers once the benchmark produces them.*

## Paper 6: Multi-Agent Design / MASS (Zhou et al., 2025)

- **Paper:** "Multi-Agent Design: Optimizing Agents with Better Prompts and Topologies"
- **Link:** https://arxiv.org/abs/2502.02533
- **Authors / venue:** Han Zhou, Xingchen Wan, Ruoxi Sun, Hamid Palangi, Shariq Iqbal, Ivan Vulić, Anna Korhonen, Sercan Ö. Arık (Google DeepMind & University of Cambridge). Submitted Feb 2025; later version accepted to ICLR 2026.

**What it does:** Studies how agent topology (how agents communicate) and prompt quality affect multi-agent system performance, and proposes MASS, a search framework that jointly optimizes prompts and topology. Finds prompts and topology are both critical to effective MAS design.

**What we adopted:**
- Hybrid orchestrator topology → our orchestrator uses centralized control (Planner decides, orchestrator routes) with no agent-to-agent communication. Agents do not talk to each other — the orchestrator mediates all data flow.
- "Architecture and prompts matter, not just model choice" → we invested heavily in prompt engineering per agent rather than using a more expensive LLM.

## Paper 7: Fingerprinting AI Coding Agents (Ghaleb, MSR 2026)

- **Paper:** "Fingerprinting AI Coding Agents on GitHub"
- **Link:** https://arxiv.org/abs/2601.17406
- **Author / venue:** Taher A. Ghaleb (sole author). Mining Software Repositories (MSR) 2026.
- **Replication:** https://github.com/Taher-Ghaleb/AIAgentsFingerprinting-MSR2026

**What it does:** Studies fingerprinting of AI coding agents across 33,580 pull requests from five agents (OpenAI Codex, GitHub Copilot, Devin, Cursor, Claude Code), using a feature set spanning commit messages, PR structure, and code characteristics (the paper reports 53 features across five categories). Achieves 97.2% F1-score in identifying which agent produced a change.

**What we adopted:**
- Feature-engineering methodology → our `pattern_extractor.py` implements a subset of code-characteristic features: comment density, comment-style ratio, conditional density, loop density, comprehension ratio, Gini coefficient for change concentration, indentation consistency, line-length statistics, import density. These are layered on top of our original features.
- The insight that code has a quantifiable "fingerprint" — originally used for AI-agent detection, which we repurpose for developer style profiling.

**What we changed:**
- Ghaleb uses fingerprinting to detect *AI agents*. We use it to learn *human developer* patterns.
- We skipped the PR/commit/temporal features (relevant to agent detection, not developer style).

## Paper 8: Multi-Granularity Code Fingerprinting (Ringer model, 2025)

- **Paper:** "A privacy-preserving standardized model for large-scale source code fingerprint extraction and clone detection" (the model is named *Ringer*).
- **Link:** https://www.sciencedirect.com/science/article/abs/pii/S0920548925000273
- **Venue:** Computer Standards & Interfaces, 2025.
- **⚠ Confirm before citing:** verify the exact author list and page numbers directly from the ScienceDirect page. ("Ringer" is the *tool name*, not an author.)

**What it does:** A privacy-preserving code-clone-detection model that uses **multi-granularity fingerprinting at file and statement levels** to improve detection efficiency and precision (reported to surpass tools like Moss and Nicad), across multiple languages. *(This paper addresses clone detection, not authorship attribution — do not describe it as an authorship-attribution paper.)*

**What we adopted:**
- The multi-granularity fingerprinting idea (representing code at more than one level of granularity) → our `embedder.py` stores embeddings at both **file-level and function-level** with a granularity metadata field.
- This motivates our two-stage retrieval: `query_similar_staged()` first retrieves relevant files, then retrieves specific functions within them, giving the Style Analyst both broad context and precise matches.

**What we changed / what is ours (not from the paper):**
- The paper targets clone detection; we apply the multi-granularity idea to **style-aware retrieval for review**.
- The use of **ChromaDB** for vector storage and the Jina v2 embeddings are PersonaCR's own design choices — do **not** attribute the ChromaDB storage to this paper.

## Paper 9: LLM + Static Analysis at Ericsson (Ramesh, Bose et al., 2025)

- **Paper:** "Automated Code Review Using Large Language Models at Ericsson: An Experience Report"
- **Link:** https://arxiv.org/abs/2507.19115
- **Venue:** Industry experience report (also appears in IEEE Xplore), 2025.

**What it does:** Documents Ericsson's experience deploying LLM-based code review in production, combining LLMs with static program analysis, plus prompt engineering and a validation mechanism to reduce hallucination and verbosity.

**What we adopted:**
- LLM + static-analysis combination → our Defect Hunter combines Python AST analysis (local, instant) with Groq LLM analysis (semantic, deeper). Our pseudo-reference generator similarly combines AST analysis with LLM claims.
- Industry validation that combining LLMs with static analysis is the practical direction for production code review.

*Note: describe the "personalized multi-agent framework" as PersonaCR's own extension of this direction, rather than implying the Ericsson paper called for exactly that.*

## Research Gap — PersonaCR's Contribution

After reviewing major venues (EMNLP, NAACL, ACL, ICSE, ASE, MSR):
- Personalized code *generation* exists (MPCoder) but not personalized *review*.
- Multi-agent code *review* exists (CodeAgent, RevAgent) but without personalization.
- No published paper combines both — this is PersonaCR's contribution at the *research* level.

PersonaCR bridges this gap by:
- Learning per-developer coding patterns (MPCoder concept applied to the review domain).
- Reviewing with specialized parallel agents (CodeAgent + RevAgent architecture).
- Self-evaluating review quality (CRScore methodology).
- Optimizing for latency on the critical path (LAMaS principles).
- Exposing everything via MCP for editor integration.

**Honesty note (read before an interview):** The "no paper combines both" claim is about the *academic literature* and is defensible there. It is **not** true of the commercial market — tools such as Greptile, Kodus/Kody, CodeRabbit, Qodo, and Cursor Bugbot already ship personalized / codebase-aware review. The honest framing is twofold: (1) the *research gap* is real, and (2) PersonaCR's *mechanism* is distinctive — it learns style from an **AST fingerprint of the code itself**, whereas most commercial tools learn from a team's **past PR-comment history**. Claim that specific distinction; avoid claiming "nobody has built personalized review."
